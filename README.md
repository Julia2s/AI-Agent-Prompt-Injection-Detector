# Конвейер обработки задач с противодавлением (FastStream + RabbitMQ + MLflow)

```
CSV-источник ─┐                                   ┌─> PostgreSQL (результаты, UNIQUE task_id)
              ├─> RabbitMQ: очередь x-max-length ─┤
POST /tasks ──┘   (reject-publish, confirms)      └─> worker(ы) FastStream, модель из MLflow
                                                      └─> DLQ (<queue>.dlq)
```

## Запуск

```bash
cp .env.example .env
docker compose up --build -d
docker compose logs -f data-pipeline train worker
```

`data-pipeline` готовит данные, `train` обучает модель и назначает alias `champion`,
затем стартует `worker`. Первый запуск занимает несколько минут.

| Интерфейс | Адрес |
|---|---|
| API / Swagger | http://localhost:8000/docs |
| RabbitMQ Management | http://localhost:15672 (`guest` / `guest`) |
| MLflow | http://localhost:5000 |

Чистый старт: `docker compose down -v`. Если том PostgreSQL остался от старой версии,
схема обновится сама (`ALTER TABLE ... IF NOT EXISTS` в `ResultStore.initialize`).

## 1. Архитектура

`mlops/producer.py`, `mlops/worker.py` и `src/` (API) -- независимые процессы, связанные
только через RabbitMQ и БД. Источник не обращается к воркеру: обратная связь приходит
только от брокера. Воркер грузит `models:/<MODEL_NAME>@<MODEL_ALIAS>` один раз в
`lifespan`; версия нигде не зашита. `INFERENCE_DELAY` (по умолчанию 0,5 с) -- искусственная
задержка поверх реального времени модели, она делает условия воспроизводимыми.

## 2. Брокер → воркер

`PREFETCH_COUNT = WORKER_CONCURRENCY = 1`. Значение выводится, а не подбирается:

- Модель -- sklearn и держит GIL, параллелизм воркера равен размеру `ThreadPoolExecutor`
  (`C = WORKER_CONCURRENCY`) и семафора на `C` слотов.
- Пропускная способность одного воркера ≈ `C / T`, где `T = INFERENCE_DELAY + t_model + t_DB`.
  При `C=1`, `T≈0,5 с` это ≈ 2 задачи/с.
- Неподтверждённых сообщений у воркера должно быть ровно столько, сколько он реально
  обрабатывает. Меньше `C` -- слоты простаивают в ожидании сети. Больше `C` -- лишние
  `prefetch − C` сообщений лежат «в кармане» одного воркера: второй воркер их не получит
  (плохое распределение), при падении они возвращаются в очередь, при остановке их приходится
  ждать, а в памяти процесса растёт буфер. Несогласованные значения отклоняются при старте;
  `0` (без ограничения) разрешён только для baseline-эксперимента (раздел 7).

Inference выполняется в `ThreadPoolExecutor` через `run_in_executor`, `time.sleep` --
только внутри потока. Event loop остаётся свободным; доказательство -- health-check воркера:

```bash
docker compose exec worker python -c "import urllib.request; print(urllib.request.urlopen('http://localhost:8001/healthz', timeout=2).status)"
```

Запускайте во время обработки с `INFERENCE_DELAY=5`: ответ `200` приходит мгновенно. Для
чисто Python CPU-bound модели нужны процессы (`ProcessPoolExecutor`): потоки не обходят GIL.

## 3. Воркер → источник

Durable-очередь `x-max-length=50`, `x-overflow=reject-publish`; публикации persistent,
mandatory, с publisher confirms. При переполнении брокер отвечает `basic.nack` на
конкретную публикацию. Источник держит **одну** текущую задачу и повторяет её через
асинхронную задержку 0,5 → 1 → 2 с; следующая строка CSV не читается до подтверждения
предыдущей. Внутреннего буфера и фиксированной частоты нет: источник замедляется ровно
настолько, насколько воркеры освобождают места.

Установившийся режим: принятая скорость источника = пропускная способность воркеров
`W · C / T`. Второй воркер увеличивает её вдвое без изменения кода.

Лимит относится к `messages_ready`. Неподтверждённые сообщения (у каждого воркера до `C`)
в лимит не входят, поэтому `ready + unacked ≤ 50 + W·C`.

**Почему именно так, и что отвергнуто**

| Вариант | Причина отказа |
|---|---|
| Опрос Management API | устаревшее значение (статистика обновляется раз в 1–5 с), гонка между несколькими источниками, лишний HTTP на каждую публикацию |
| Фиксированный rate limit | это rate limiting, не backpressure: не знает ни числа воркеров, ни их скорости |
| `x-overflow: drop-head` | брокер молча выбрасывает уже принятые задачи |
| Неограниченная очередь / буфер в источнике | перенос проблемы в память брокера или источника (см. эксперимент) |
| Credit-based flow control (AMQP 1.0, Streams) | сложнее и не нужен: confirms + reject-publish дают сигнал на каждую публикацию |

При сетевом timeout неизвестно, принял ли брокер сообщение. Источник повторяет тот же
`task_id`, дубль безвреден благодаря `UNIQUE(task_id)`. При аварии источника CSV остаётся
на диске: повторный запуск с тем же `batch-id` восстановит пакет.

## 4. Граница системы: `POST /api/v1/tasks`

| Ответ | Когда |
|---|---|
| `202` + `Location` | задача принята брокером (подтверждение получено), статус `PENDING` |
| `200` | такой `task_id` уже выполнен -- возвращается результат, публикации нет |
| `409` | `task_id` уже использован с другим текстом |
| `422` | невалидное тело |
| `503` + `Retry-After` | очередь переполнена, брокер/БД недоступны или таймаут подтверждения |

`GET /api/v1/tasks/{task_id}` → `PENDING` / `SUCCESS` (с `label`, `inference_ms`, `latency_ms`) / `404`.

Порядок: 1) запись `PENDING` (коммит), 2) публикация с confirm (не дольше `PUBLISH_TIMEOUT`,
без цикла ожидания), 3) подтверждено → `202`; отказ → удалить `PENDING` (компенсация) и `503`.
После любого `503` в БД нет строки `PENDING` (проверяется тестами, в том числе на реальных
RabbitMQ и PostgreSQL). Если сама компенсация не удалась, повтор запроса с тем же `task_id`
безопасно публикует задачу заново.

`Retry-After = max(1, ceil(INFERENCE_DELAY + RETRY_DELAY))`: за это время один воркер
освобождает слот (inference) плюс пауза перед повторной выдачей. Это подсказка, не обещание:
другие клиенты и источник могут занять освободившееся место.

**Почему это load shedding, а не backpressure.** Противодавление -- замкнутый контур: поставщик
подчиняется системе и сам замедляется, а задача сохраняется (CSV-источник держит её и повторяет).
У внешнего HTTP-клиента контур разомкнут: мы не можем заставить его ждать, а если держать
соединение, запросы копятся в памяти API и таймаутах клиентов -- то же неограниченное накопление.
Поэтому система отбрасывает лишнюю нагрузку, сообщая об этом (`503`), а ответственность за повтор
переходит клиенту. Задача не остаётся в системе.

## 5. Ошибки и надёжность

- `AckPolicy.NACK_ON_ERROR`: возврат из обработчика = ack, исключение = nack с requeue.
  ACK происходит **после** коммита результата (или подтверждённой публикации в DLQ).
  `ACK_FIRST` отвергнут: падение после ack теряет задачу. Безусловный ack на ошибке тоже теряет.
  Безусловный reject без повтора не лечит временные сбои.
- Счётчик неудач хранится в `task_failures` и переживает редоставку и рестарт воркера.
  После `MAX_ATTEMPTS=3` сообщение идёт в `<QUEUE_NAME>.dlq`. Перед nack -- `RETRY_DELAY`, busy loop нет.
  Невалидный JSON/схема -- сразу в DLQ (повтор не исправит формат).
- Идемпотентность: `UNIQUE(task_id)` и атомарный upsert `PENDING → SUCCESS`
  (`INSERT ... ON CONFLICT DO UPDATE ... WHERE status='PENDING'`): готовый результат не
  перезаписывается, гонка решается БД, а не проверкой «прочитать, затем вставить».
- Падение между коммитом и ack → повторная доставка без дубля. Публикация в DLQ и ack не атомарны:
  возможен дубль записи в DLQ (at-least-once), у него стабильный `message_key`.
- **Graceful shutdown.** FastStream при SIGTERM перестаёт брать новые сообщения и ждёт
  принятые не дольше `GRACEFUL_TIMEOUT` (по умолчанию 300 с, меньше `stop_grace_period: 10m`).
  Важно: `graceful_timeout=None` в FastStream 0.7 означает «не ждать» -- работающий handler
  отменяется (проверено, регрессионный тест `test_graceful_timeout_is_a_real_number` и
  интеграционный `test_sigterm_finishes_accepted_message`).

Проверка graceful shutdown под нагрузкой:

```bash
docker compose --profile load run --rm -d producer
docker compose logs -f worker &           # видно Received ... затем Processed после stop
docker compose stop worker && docker compose start worker
```

В Management UI: `unacked` → 0 только после завершения, потерь и дублей нет
(`SELECT count(*), count(DISTINCT task_id) FROM task_results`).

## 7. Экспериментальное исследование

Сценарии запускаются одним скриптом, воркеры масштабируются без правки кода:

```bash
docker compose up --build -d                 # стек + модель уже готовы

scripts/experiment.sh unbounded-1w unbounded 1 30            # без защиты, 1 воркер
scripts/experiment.sh bounded-1w   bounded   1 60            # с защитой, 1 воркер
scripts/experiment.sh bounded-2w   bounded   2 60            # с защитой, 2 воркера
scripts/experiment.sh bounded-scale bounded  1 90 45         # 1 воркер, на 45-й секунде +1

uv run python scripts/report.py \
  --run "без ограничений, 1 воркер=runs/unbounded-1w" \
  --run "с ограничениями, 1 воркер=runs/bounded-1w" \
  --run "с ограничениями, 2 воркера=runs/bounded-2w" \
  --run "с ограничениями, 1→2 воркера=runs/bounded-scale" \
  --limit 50 --out runs/report
```

`unbounded` -- намеренно плохая конфигурация: очередь без `x-max-length`, `prefetch=0`,
источник в режиме `naive` (каждая строка сразу становится asyncio-задачей, никто не ждёт
брокера). Код воркера и источника тот же, меняются только настройки и режим.

Что измеряется (`scripts/monitor.py`, раз в секунду; Management API здесь **наблюдатель**,
система по нему не управляется, поэтому п. 3 не нарушен):

| Показатель | Источник данных | График |
|---|---|---|
| глубина очереди (ready + unacked) | Management API, `messages_ready` / `unacked` | `queue_depth.png` |
| длина очереди vs лимит | Management API, `messages_ready` | `queue_ready.png` (с пунктиром `x-max-length`) |
| память воркера, брокера | `docker stats` | `mem_worker_mb.png`, `mem_rabbitmq_mb.png` |
| память и буфер источника | сам источник (RSS, число задач в памяти) | `source_rss.png`, `source_buffer.png` |
| скорость источника (принято брокером) | метрики источника | `source_rate.png` |
| скорость воркеров | Management API, `ack_per_s` | `worker_rate.png` |
| время задачи | БД: `inference_ms`, `latency_ms` (создание → результат) | `latency.png` |

Заметки по интерпретации:

- Счётчик `publish` брокера считает и **отклонённые** публикации, поэтому скорость источника
  берётся из его собственных метрик (`accepted_per_s`), а не из Management API.
- Латентность считается только по **завершённым** задачам; невыполненные из переполненной
  очереди в неё не попадают. Оценка ожидания хвоста: `глубина / ack_per_s`.
- В режиме `unbounded` обратите внимание на скорость самого воркера: тысячи
  предвыбранных сообщений превращаются в asyncio-задачи, и `inference_ms` растёт.

### Результаты

Параметры прогона: `INFERENCE_DELAY=0.5`, `QUEUE_CAPACITY=50`, `PREFETCH_COUNT=1`,
`WORKER_CONCURRENCY=1`, длительность сценария 30–90 с + дренаж 20 с. Все 4 сценария
прогнаны против одного и того же стека и модели `models:/prompt-injection-detector@champion`.

Графики лежат в `runs/report/` (`queue_depth.png`, `queue_ready.png`, `source_rate.png`,
`worker_rate.png`, `mem_worker_mb.png`, `mem_rabbitmq_mb.png`, `source_rss.png`,
`source_buffer.png`, `latency.png`), числовая сводка — `runs/report/summary.md`.
Заметка об устойчивых средних: `report.py` для steady-state берёт вторую половину
активного окна и отбрасывает сэмплы, где брокер показал `publish_per_s = ack_per_s = 0`
(артефакт интервала обновления статистики RabbitMQ Management API) — иначе среднее
занижалось бы в 1,5–2 раза.

|---|---|---|---|---|

**Про колонку «1→2 воркера».** Сценарий `bounded-scale` стартует с одним воркером и
на 45-й секунде добавляет второй через `docker compose up --scale worker=2 --no-recreate`
— без перезапуска и без правки кода. `report.py` для steady-state берёт вторую половину
активного окна (45–90 с), которая в этом сценарии смешивает «медленный» и «быстрый»
периоды, поэтому `ack/с = 3,68` — это среднее между ~2/s (до 45 с) и ~4/s (после), а не
стационар. Скачкообразное удвоение пропускной способности лучше всего видно на графиках
`runs/report/source_rate.png` и `worker_rate.png`: на 45-й секунде `accepted_per_s`
меняется с ~2 на ~4, и `ack/s` делает то же самое. Число завершённых задач за 90 с (287)
близко к сумме «1 воркер за 45 с + 2 воркера за 45 с» ≈ 90 + 180 = 270 — то есть
масштабирование сработало именно так, как ожидалось. Латентность p95 = 29,7 с объясняется
тем, что в steady-state попадают задачи, вставшие в очередь ещё в «медленном» периоде
и простоявшие 20+ секунд, прежде чем их успел обработать один воркер.

### Выводы

1. **Без ограничений очередь и память неконтролируемо растут.** За 50 с источник
   отправил в брокер десятки тысяч сообщений, из которых воркер успел обработать
   лишь 74. Глубина очереди достигла 41 870 (ready + unacked), а в памяти источника
   скопилось 27 964 задач — то самое неограниченное накопление, против которого
   направлена работа. RabbitMQ вырос до 447 МиБ, воркер — до 699 МиБ. Это
   демонстрирует, что «убрать backpressure» — это не «работать медленнее», а
   «перенести очередь в оперативную память процесса-отправителя и брокера».

2. **Скорость источника сходится к пропускной способности воркеров.** При одном
   воркере `ack/с ≈ 2,15` (теоретический максимум `1 / INFERENCE_DELAY = 1 / 0,5 = 2,0`
   с небольшим запасом за счёт конвейеризации publisher-confirm и записи в БД),
   и источник стабилизировался на 1,9 принятых задач/с — ровно столько, сколько
   воркер успевает обработать (микрозанижение в десятых — источник делает паузу
   на повтор публикации после каждого nack). Подтверждается механика: очередь
   держится на лимите 50, ровно половина публикаций отклоняется брокером
   (`rejected publish attempts = 114`), источник повторяет их с экспоненциальной
   паузой 0,5→2 с и не теряет ни одной.

3. **Добавление второго воркера удваивает пропускную способность без правки кода.**
   В статическом сценарии `ack/с` вырос с 2,15 до 4,31 (×2,01), `publish`-попытки/с
   на брокере выросли с 4,31 до 6,46, глубина очереди осталась на уровне 50, потерь
   по-прежнему ноль, а число завершённых задач выросло с 144 до 281 (×1,95). Это и
   есть «источник автоматически согласуется с совокупной пропускной способностью
   воркеров»: код не трогали, просто добавили реплику через `--scale worker=2`.
   Скорость источника при этом выросла с 1,9 до 3,87 принятых/с (×2,04) — то есть
   на 2 воркера он ускорился ровно во столько же раз, во сколько ускорился сам воркер.

4. **Масштабирование «на лету» работает без рестарта.** В сценарии `bounded-scale`
   на 45-й секунде к уже работающему воркеру добавили второй — код не пересобирали,
   очередь не пересоздавали, источник не перезапускали. График `source_rate.png`
   чётко показывает, как `accepted_per_s` в этот момент удваивается с ~2 до ~4,
   а `worker_rate.png` — как `ack/s` делает тот же скачок. Число завершённых задач
   за 90 с (287) близко к сумме «1 воркер за 45 с» + «2 воркера за 45 с». Это
   ключевой практический эффект замкнутого контура противодавления: ёмкость
   регулируется операционно, без выкладки нового кода.

5. **Латентность ведёт себя ожидаемо.** Без ограничений p95 достигает 48,8 с
   (сообщения подолгу лежат в очереди), с одним воркером — 29,9 с (50 сообщений в
   очереди × 0,5 с inference ≈ 25 с ожидания), с двумя — 16,5 с (та же глубина, но
   обрабатывается в два потока). `inference_ms` остаётся стабильным (~508 мс),
   что подтверждает: при bounded-prefetch воркер не захлёбывается asyncio-задачами,
   как в unbounded-режиме, где `inference_ms` разбухает до 554 мс из-за
   конкуренции prefetch-буфера за CPU.

6. **Чем платит система за ограничение.** Источник простаивает, когда очередь
   полна: ровно половина попыток публикации отклоняется и повторяется через
   0,5–2 с. Внешний HTTP-клиент при перегрузке немедленно получает 503 — это
   плата за load shedding вместо неограниченного ожидания. Память брокера и
   воркера ограничена (250–503 МиБ против 447–699 МиБ), источник стабилен на
   55 МиБ RSS вместо 304 МиБ. Цена — в снижении пиковой скорости источника до
   скорости воркеров, но именно это и обеспечивает устойчивость системы.

## Конфигурация

Основные значения -- `.env.example` и `mlops/settings.py`; compose подставляет их из `.env`.

RabbitMQ не позволяет менять `x-max-length` redeclare-ом. Для другого лимита: остановить
источники, дождаться `ready = unacked = 0`, остановить worker/API, удалить пустую очередь
в Management UI, поменять `.env`, пересоздать сервисы (или задать новый `QUEUE_NAME`).
Непустые очереди и тома не удалять.

## Структура

- `mlops/settings.py`, `messaging.py` -- настройки и топология.
- `mlops/producer.py`, `mlops/metrics.py` -- источник, режимы `backpressure`/`naive`, метрики.
- `mlops/worker.py` -- загрузка модели, inference, ретраи, DLQ, health.
- `mlops/db.py` -- PENDING/SUCCESS, атомарный upsert, счётчик ошибок, времена.
- `src/api/v1/routes/tasks.py` -- HTTP-граница (load shedding).
- `scripts/` -- `monitor.py`, `report.py`, `experiment.sh`.
- `tests/` -- юнит- и интеграционные тесты.
